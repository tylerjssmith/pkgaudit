Getting Started with pkgaudit

pkgaudit is a static analysis security testing (SAST) tool for R source packages. It flags security-relevant files and R source code for manual review, and organizes what it finds by the point in the R package lifecycle at which the code runs (e.g., build, check, install, load).

A finding is not an accusation. Most flagged code is legitimate: packages compile source code, download data, and call shell tools for good reasons. The purpose of a scan is to tell you which parts of an unfamiliar package deserve your attention before you install and load it.

library(pkgaudit)

pkgaudit Rules

pkgaudit v0.3.0 separates when code executes from what code does using three types of rules:

  • File contexts are files that R executes at build-, check-, or install-time, such as configure and src/Makevars.
  • Code contexts are top-level R source code and lifecycle hooks whose bodies run automatically when a namespace is loaded, attached, unloaded, or detached, such as .onLoad() and .onAttach().
  • Patterns are security-relevant function calls, such as system(), which can execute arbitrary shell commands.

The three combine to give a finding its weight. A system() call inside an ordinary function only runs if you call that function; the same call inside .onLoad() runs the moment the namespace loads. Every pattern finding is therefore attributed to the code context that contains it.

The full rule set is documented in RULES.md.

An Example Package

As a demonstration, we will build a small source package that does several things a reviewer would want to know about, and scan that.

pkg <- file.path(tempdir(), "riskypkg")
dir.create(file.path(pkg, "R"), recursive = TRUE, showWarnings = FALSE)

writeLines(c(
  "Package: riskypkg",
  "Title: An Example Package",
  "Version: 0.1.0",
  "Description: A small package used to demonstrate pkgaudit.",
  "License: MIT + file LICENSE"
), file.path(pkg, "DESCRIPTION"))

# A configure script runs at install time, before any R code is loaded.
writeLines(c("#!/bin/sh", "echo configuring"), file.path(pkg, "configure"))

# .onLoad() runs automatically when the namespace is loaded.
writeLines(c(
  ".onLoad <- function(libname, pkgname) {",
  '  system("uname -a")',
  "}"
), file.path(pkg, "R", "zzz.R"))

# An ordinary function only runs if the user calls it.
writeLines(c(
  "fetch_data <- function(url) {",
  "  download.file(url, tempfile())",
  "}"
), file.path(pkg, "R", "fetch.R"))

Working with pkgaudit Results

A pkgaudit object is a named list of ordinary data frames, so you can filter, join, and report on the findings however you like.

result$file_contexts
#>   file_context file_path
#> 1    configure configure
#>                                                                                                                                                 message
#> 1 configure is a shell script used for system-dependent configuration when packages are installed from source. It can execute arbitrary shell commands.
result$code_contexts
#>   code_context file_context line_number column_number
#> 1  onload_code      R/zzz.R           1             1
#>                                                                                                                            message
#> 1 .onLoad() executes arbitrary code when a package namespace is loaded, e.g., by calling library(), require(), or loadNamespace().
result$patterns
#>                 pattern file_context line_number column_number
#> 1 download_file_pattern    R/fetch.R           2             3
#> 2        system_pattern      R/zzz.R           2             3
#>                                                                                                                                                                message
#> 1 download.file() and url() retrieve or open a connection to a remote resource. This can stage a payload for execution via source() or system() in a two-stage attack.
#> 2                                                                              system(), system2(), shell() (on Windows), and pipe() execute arbitrary shell commands.
#>                           attck code_context
#> 1               T1105 T1195.002        Other
#> 2 T1059.003 T1059.004 T1195.002  onload_code

Each row of result$patterns carries the code context it was found in, so the distinction that matters most is a single subset away:

result$patterns[result$patterns$code_context == "onload_code", ]
#>          pattern file_context line_number column_number
#> 2 system_pattern      R/zzz.R           2             3
#>                                                                                   message
#> 2 system(), system2(), shell() (on Windows), and pipe() execute arbitrary shell commands.
#>                           attck code_context
#> 2 T1059.003 T1059.004 T1195.002  onload_code

Auditing a Tarball

The more common workflow is to scan a package you have not yet installed. audit_tarball() takes a .tar.gz source package, validates it, extracts it to a temporary directory, and scans the result.

tarball <- file.path(tempdir(), "riskypkg_0.1.0.tar.gz")

# Archive the package by its directory name, so the tarball holds relative paths
owd <- setwd(dirname(pkg))
utils::tar(tarball, files = basename(pkg), compression = "gzip", tar = "internal")
setwd(owd)

audit_tarball(tarball)
#> --- pkgaudit -------------------------------------------------------------------
#> Package:        riskypkg v0.1.0 (source tarball)
#> Path:           /var/folders/27/q80w2y5j11l6qq8xwf90y5q00000gq/T//RtmpfQzYgu/riskypkg_0.1.0.tar.gz
#> SHA-256:        c0a3051ac349ffd6ce18a81bf81ebe203da66a740ecae3f8b9adc1169d00b37c
#> Scanned:        2026-07-28 19:27 UTC with pkgaudit 0.3.0, rules v0.2.0
#> 
#> File contexts:  1
#> Code contexts:  1
#> Patterns:       2
#> Errors:         0

Because an untrusted archive is itself an attack surface, the tarball is checked before anything is written to disk. validate_tar() performs that check on its own, and rejects archives with absolute paths, paths escaping the extraction directory, or symlinks pointing outside it. It also enforces limits on entry count, uncompressed size, and compression ratio, guarding against archives that expand to exhaust the disk:

str(validate_tar(tarball))
#> 'data.frame':    5 obs. of  4 variables:
#>  $ name    : chr  "riskypkg/configure" "riskypkg/DESCRIPTION" "riskypkg/R/" "riskypkg/R/fetch.R" ...
#>  $ type    : chr  "file" "file" "dir" "file" ...
#>  $ linkname: chr  "" "" "" "" ...
#>  $ size    : int  27 146 0 65 63

Rules and Database Integrity

The rules live in a versioned SQLite database shipped with the package. load_rules() reads it, and rules_version() reports the version:

rules_version()
#> [1] "0.2.0"

rules <- load_rules()
nrow(rules$file_contexts)
#> [1] 16
nrow(rules$code_contexts)
#> [1] 6
nrow(rules$patterns)
#> [1] 16

Passing the rules explicitly avoids re-reading and re-verifying the database on every call, which is worthwhile when scanning many packages:

rules   <- load_rules()
results <- lapply(tarballs, audit_tarball, rules = rules)

Because the rules determine what a scan can find, a modified database is a way to make a scan come back clean. load_rules() verifies the database against its bundled SHA-256 sidecar on every call and refuses to load a modified one. You can also check the hash of your installed copy against the value published in README:

digest::digest(
  system.file("db", "rules.db", package = "pkgaudit"),
  algo = "sha256",
  file = TRUE
)
#> [1] "aaf0336597a4b4c82242a234876364b44b54da324f3b48f100aaa0e3a6a1a9aa"

Interpreting a Scan

A clean scan is weak evidence of safety: pkgaudit reasons about syntax, so sufficiently indirect code can evade any pattern rule. A scan with findings is better understood as a reading list than a verdict. In review, the questions worth asking are roughly:

  • Does the package need this capability at all, given what it claims to do?
  • Does it run without being asked, at install or load time, rather than when a user calls a function?
  • Does it reach the network, and if so, is the destination fixed and identifiable in the source?
  • Is the code being run visible in the source, or is it assembled, decoded, or fetched at runtime?

Findings that answer badly on several of these at once are the ones to read closely.
